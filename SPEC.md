# Спецификация

## Что делаем

Однопользовательский REST API списка задач на Laravel 12 и PHP 8.2. Данные
хранятся в локальном JSON-файле, без базы данных и внешних сервисов.

## Для кого и зачем

API предназначен для одного пользователя, которому нужно создавать, просматривать,
изменять и удалять личные задачи. Регистрация, авторизация и разделение задач между
пользователями не требуются.

## Сущность задачи

Задача содержит:

- `id` — положительное целое число, назначается сервером;
- `title` — обязательная строка длиной от 1 до 200 символов после удаления пробелов
  по краям;
- `description` — необязательная строка длиной до 2000 символов или `null`;
- `status` — одно из `todo`, `in_progress`, `done`; по умолчанию `todo`;
- `due_date` — необязательная календарная дата в формате `YYYY-MM-DD` или `null`;
- `category_id` — положительный идентификатор категории или `null`; по умолчанию
  `null`;
- `created_at` — время создания в UTC, формат ISO 8601;
- `updated_at` — время последнего изменения в UTC, формат ISO 8601.

Дата выполнения может находиться в прошлом. Переходы между статусами не
ограничены.

## Сущность категории

Категория содержит серверный положительный `id`, имя `name`, `created_at` и
`updated_at`. Имя обязательно, обрезается по краям, имеет длину 1–100 символов и
уникально без учёта регистра. Задача принадлежит максимум одной категории; задача
без категории допустима.

## Контракт API

Все успешные ответы с одной задачей (`GET`, `POST`, `PATCH`) возвращают объект
задачи в единой оболочке `{"data": {...}}`. Ответ списка использует ту же оболочку
с массивом: `{"data": [...]}`.

API имеет версию `v1`. Неверсионированные маршруты не поддерживаются.

### `GET /api/v1/tasks`

Возвращает все задачи по возрастанию `id` в теле `{"data": [...]}`.

Поддерживает необязательные query-параметры `statuses`, `due_date` и
`category_ids`:

- несколько статусов передаются массивом, например
  `statuses[]=todo&statuses[]=done`, и объединяются через OR;
- `due_date` принимает одну точную дату `YYYY-MM-DD`;
- `category_ids` передаётся непустым списком уникальных положительных целых;
  категории внутри списка объединяются через OR;
- группы статусов, даты и категорий объединяются через AND;
- задача с `due_date: null` не совпадает с заданной датой;
- задача с `category_id: null` не совпадает с заданными категориями.

Без фильтров возвращаются все задачи. Пустая выборка возвращает `200` и
`{"data": []}`. Пустые массивы, повторяющиеся или неверные элементы фильтров,
неизвестные статусы, неверная дата, старый параметр `status` и другие неизвестные
параметры возвращают `422`.

### `GET /api/v1/tasks/{id}`

Возвращает `{"data": {...}}` с задачей и кодом `200`. Для несуществующего
идентификатора возвращает `404`.

### `POST /api/v1/tasks`

Создаёт задачу и возвращает `{"data": {...}}` с ней и кодом `201`. Клиент может
передать `title`, `description`, `status`, `due_date` и `category_id`. Категория
может быть `null`; неизвестная категория возвращает `422`. Неизвестные и
серверные поля запрещены.

### `PATCH /api/v1/tasks/{id}`

Частично изменяет `title`, `description`, `status`, `due_date` или `category_id`.
Неизвестная категория возвращает `422`. В теле должно
быть хотя бы одно допустимое поле. Поля `id`, `created_at` и `updated_at` менять
нельзя. Повторная отправка уже сохранённых значений возвращает `200` и
`{"data": {...}}` с текущей неизменённой задачей. Для несуществующего
идентификатора возвращается `404`.

### `DELETE /api/v1/tasks/{id}`

Физически удаляет задачу и возвращает `204` без тела. Корзины и восстановления
нет. Для несуществующего идентификатора возвращается `404`.

### Категории

- `GET /api/v1/categories` — список категорий по возрастанию `id`;
- `GET /api/v1/categories/{id}` — одна категория или `404`;
- `POST /api/v1/categories` — создание по единственному полю `name`, ответ `201`;
- `PATCH /api/v1/categories/{id}` — изменение имени, ответ `200`;
- `DELETE /api/v1/categories/{id}` — `204`; для используемой категории —
  `409 category_in_use` без изменения задач и файла.

Повтор имени без учёта регистра возвращает `422 validation_failed`.

## Валидация и ошибки

Неизвестные поля запроса запрещены. Все найденные ошибки валидации возвращаются
вместе с кодом `422`:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Request validation failed",
    "details": [
      {
        "field": "title",
        "message": "The title field is required."
      }
    ]
  }
}
```

Ошибки без привязки к полю содержат пустой массив `details`. Невалидный JSON
возвращает `400`, отсутствующая задача — `404`, ошибка или повреждение хранилища
— `500`. Трассировки стека наружу не возвращаются. Удаление используемой
категории возвращает `409`.

## Файловое хранилище

Рабочий файл: `storage/app/tasks.json`. Формат:

```json
{
  "next_task_id": 1,
  "next_category_id": 1,
  "tasks": [],
  "categories": []
}
```

Счётчики выдают идентификаторы соответствующим сущностям, затем увеличиваются.
Удалённые идентификаторы не используются повторно. Запись выполняется атомарно и
с блокировкой файла.

- отсутствующий файл считается пустым хранилищем и создаётся при первой записи;
- пустой файл считается пустым хранилищем;
- старый валидный формат с `next_id` и `tasks` читается без изменения файла;
  каждой старой задаче в памяти назначается `category_id: null`, а новый формат
  атомарно записывается при следующем успешном изменении;
- невалидный JSON, неверная корневая структура или некорректные служебные поля
  считаются повреждением;
- повреждённый файл не перезаписывается, API возвращает `500` с кодом
  `storage_corrupted`.

## Состояния и сценарии

1. Пользователь создаёт корректную задачу и получает сохранённую задачу с `id`,
   временными метками и кодом `201`.
2. Пользователь создаёт категории, распределяет задачи и комбинирует несколько
   статусов, категорий и точную дату выполнения.
3. Пользователь получает пустой список при отсутствии совпадений.
4. Пользователь частично обновляет существующую задачу, включая повторную отправку
   тех же значений.
5. Пользователь удаляет существующую задачу.
6. Некорректное тело возвращает все ошибки валидации в едином формате.
7. Обращение к несуществующей задаче возвращает `404`.
8. Повреждённое хранилище возвращает безопасную ошибку и остаётся неизменным.

## Чего точно не делаем

- регистрацию, авторизацию и нескольких пользователей;
- базу данных, Eloquent-модели и миграции;
- Docker как способ запуска API;
- внешние сервисы и сетевые интеграции;
- пагинацию и пользовательскую сортировку;
- диапазоны дат и фильтрацию «до/после» срока выполнения (точное совпадение
  `due_date` реализовано);
- корзину и восстановление задач;
- приоритеты, несколько категорий/тегов у задачи, подзадачи и вложения.

## Технические решения

- Laravel 12;
- PHP 8.2;
- PHPUnit;
- Laravel Pint;
- Larastan / PHPStan level 8 без baseline и `ignoreErrors`;
- порт `8000`;
- рабочее хранилище `storage/app/tasks.json`;
- тесты используют отдельные временные файлы и не обращаются в сеть.
- HTTP-слой, бизнес-правила и JSON-хранилище разделены цепочкой
  controller → service → repository interface → JSON repository; зависимости
  разрешаются контейнером Laravel.
