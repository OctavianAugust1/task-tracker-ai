# План основной реализации

План основан на `SPEC.md`. Код из `naive-run/` не используется как основа:
наивный проект нужен только для последующего сравнения результатов.

## 1. Подготовить чистый основной Laravel-проект

- Создать Laravel 12 во временном каталоге, затем перенести его каркас в непустой
  корень проекта, не затрагивая `naive-run/`, `materials/`, `sessions/`, `SPEC.md`,
  `AGENTS.md` и неотслеживаемый `docker-compose.yml`.
- Подтвердить фактические версии PHP 8.2, Laravel 12, PHPUnit и Pint.
- Удалить или не использовать заготовки БД, миграции и Eloquent-модели.
- Подключить ровно пять API-маршрутов без дополнительных task-эндпоинтов.
- Настроить путь `storage/app/tasks.json` через конфигурацию так, чтобы тесты
  могли подменять его отдельным временным файлом.
- Проверка этапа: приложение загружается, а список маршрутов содержит ровно пять
  task API-маршрутов из предусмотренного CRUD-контракта; стандартные служебные
  маршруты Laravel проверяются отдельно и не считаются task-эндпоинтами. Отдельный
  коммит каркаса.

## 2. Зафиксировать HTTP-контракт тестами до реализации

- Создать feature-тесты для всех пяти эндпоинтов и общей оболочки `data`.
- Покрыть полный набор полей задачи, значения по умолчанию, UTC ISO 8601,
  сортировку по `id`, фильтр `status` и пустые выборки.
- Покрыть `201`, `200`, `204`, `400`, `404`, `422` и `500`, включая отсутствие
  тела у `DELETE`.
- Отдельно проверить неизвестные query-параметры, неизвестные/серверные поля,
  пустой `PATCH`, повторный идемпотентный `PATCH`, все ограничения полей и выдачу
  всех найденных ошибок в одном ответе.
- Проверить malformed JSON независимо от семантической валидации тела.
- В тестах подменять путь уникальным временным файлом; подтвердить, что рабочий
  `storage/app/tasks.json` не создаётся и не меняется, сетевых вызовов нет.
- Проверка этапа: показать ожидаемые падения контрактных тестов; отдельный коммит
  тестовой спецификации.

## 3. Реализовать единый HTTP-слой и валидацию

- Разделить обязанности: контроллер только координирует HTTP, отдельные request-
  классы валидируют `POST`, `PATCH` и query-параметры, отдельный компонент
  формирует публичные ошибки.
- Нормализовать `title` удалением пробелов по краям до проверки длины 1–200;
  проверить nullable-строки `description` до 2000 символов, enum `status` и
  строгую календарную дату `due_date` формата `YYYY-MM-DD`.
- Для `POST` разрешить только `title`, `description`, `status`, `due_date`; для
  `PATCH` — тот же allowlist и минимум одно переданное поле. Запретить неизвестные
  поля, включая `id`, `created_at`, `updated_at`.
- Возвращать ошибки в едином формате `error.code/message/details`, без HTML и
  stack trace, в том числе когда клиент не прислал `Accept: application/json`.
- Оборачивать одиночные задачи и списки в `data`; сохранить `204` без тела.
- Проверка этапа: соответствующие feature-тесты проходят; отдельный коммит
  HTTP-контракта.

## 4. Реализовать строгое JSON-хранилище

- Выделить класс хранилища с операциями `all/find/create/update/delete`; не
  использовать БД, Eloquent или внешние сервисы.
- Читать формат `{"next_id": <positive int>, "tasks": [...]}`. Отсутствующий и
  нулевой по длине файл трактовать как состояние `{next_id: 1, tasks: []}`, но не
  создавать его до первой записи.
- Валидировать JSON, точную корневую структуру, `next_id` и сохранённые записи;
  повреждение преобразовывать в безопасный `500 storage_corrupted`.
- Назначать `id` только из `next_id`, затем увеличивать счётчик; после удаления
  идентификаторы не переиспользовать. Список всегда сортировать по возрастанию
  `id`, фильтрацию выполнять только по допустимому `status`.
- На создании задавать обе UTC-метки; при фактическом изменении сохранять
  `created_at` и обновлять `updated_at`. При повторной отправке тех же значений
  вернуть неизменённую задачу без лишней записи.
- Сериализовать данные в UTF-8 JSON. Для каждой мутации удерживать блокировку на
  стабильном lock-файле на всём цикле read-modify-write, писать временный файл в
  том же каталоге и атомарно заменять целевой файл через rename. Ошибки чтения,
  блокировки, записи и замены не маскировать как пустое хранилище.
- Никогда не заменять повреждённый файл; до любой мутации сначала полностью
  прочитать и проверить текущее содержимое.
- Проверка этапа: unit/feature-тесты хранилища, включая отсутствующий, пустой,
  повреждённый файл, сохранность повреждённого содержимого и монотонность ID;
  отдельный коммит хранилища.

## 5. Закрыть пограничные и конкурентные сценарии

- Проверить несколько одновременных созданий отдельным процессным тестом или
  воспроизводимым скриптом: JSON остаётся валидным, ID уникальны, обновления не
  теряются.
- Проверить сбои файловой системы, которые можно безопасно смоделировать:
  нечитаемый файл/каталог, невозможность записи или rename; наружу должен выходить
  безопасный `500`, существующий файл не должен быть затёрт.
- Проверить, что `404` определяется после корректного чтения хранилища, а
  повреждение не превращается в ложный `404`.
- Запустить полный набор тестов и Pint; отдельный коммит граничных проверок.

## 6. Документация и приёмка

- Написать `README.md` с проверенными командами `composer install`, запуска на
  `127.0.0.1:8000`, тестов и Pint, а также кратким контрактом API.
- Выполнить `php artisan test` и `./vendor/bin/pint --test` с полным выводом.
- Поднять реальный сервис на порту 8000 с отдельным временным хранилищем;
  выполнить корректный и заведомо ошибочный HTTP-запрос, показать тела и коды.
- Вручную подтвердить поведение отсутствующего, пустого и повреждённого файла и
  неизменность повреждённого содержимого.
- Выполнить независимый аудит в чистом контексте по матрице «каждый пункт
  `SPEC.md` → маршрут/код → тест/ручное доказательство» и исправить найденные
  расхождения отдельным коммитом.
- Показать `git diff --stat`, `git status --short`, список изменённых файлов и всё,
  что осталось непроверенным. Обновить журналы и `STATE.md`.

## Отличия, которые нельзя перенести из `naive-run/`

| Область | Основная реализация |
|---|---|
| Сущность | `title`, `description`, `status`, `due_date` и обе временные метки; поля `completed` нет |
| Ответы | Всегда контрактная оболочка `data` либо единая оболочка `error` |
| Валидация | Строгий allowlist, нормализация, все ошибки вместе, malformed JSON как `400` |
| Файл | Корневой объект с `next_id` и `tasks`, а не JSON-массив |
| ID | Монотонный `next_id`, удалённые ID не используются повторно |
| Запись | Полный read-modify-write под блокировкой и атомарная замена файла |
| Повреждение | Строгая проверка структуры, `storage_corrupted`, исходный файл неизменен |
| Тесты | Полная матрица контракта и временные хранилища, а не только базовый CRUD |
