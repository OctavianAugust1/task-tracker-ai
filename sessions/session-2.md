## Размышления

Первый запрос был прерван до начала изменений. Наивный вариант нужно сохранить
отдельно от будущей основной реализации, поэтому весь Laravel-проект будет создан
в `naive-run/`. `SPEC.md` прочитан только как часть обязательной проверки состояния,
но наивная реализация не будет подгоняться под его детальный контракт: цель — получить
самостоятельный базовый результат для последующего сравнения.

План: проверить PHP и Composer; создать чистый Laravel 12 в `naive-run/`; добавить
простые CRUD-маршруты, контроллер и класс JSON-хранилища; написать минимальные тесты;
запустить тесты, Pint, сервер и ручные HTTP-проверки; отдельно проверить отсутствующий,
пустой и повреждённый файл; изучить diff, обновить журнал и `STATE.md`, затем создать
один отдельный коммит. Существующий неотслеживаемый `docker-compose.yml` не трогать.

В Ubuntu 26.04 штатный репозиторий предлагает PHP 8.5, поэтому менять требуемую
версию было бы нарушением правил. Первая попытка подключить `ppa:ondrej/php`
завершилась `404`: PPA ещё не публикует ветку `resolute` и прямо направляет её на
`packages.sury.org/php`. Нерабочая запись удалена, после чего PHP 8.2 установлен из
указанного канонического репозитория. Composer сначала падал из-за отсутствующего
`Normalizer`: метапакет `php-intl` подтянул модуль только для PHP 8.5. Установка
явного `php8.2-intl` устранила ошибку; CLI при этом остался PHP 8.2.

Первый `composer create-project` тоже не завершился: системный Composer вызвал
`array_all()`, доступную только в более новом PHP, хотя работал под 8.2. Частично
созданный каркас сохранил, а Composer заменил официальным PHAR после проверки
SHA-384. Повторный `composer install` успешно создал lock-файл и установил Laravel
12.66.0. Сгенерированные модель `User` и миграции удалены: даже для наивного прогона
они нарушали бы прямой запрет проекта на Eloquent и базу данных.

Для наивного контракта выбраны только `title` и `completed`: этого достаточно для
CRUD, а добавление полей и правил из уже утверждённого `SPEC.md` исказило бы цель
сравнения. Идентификатор вычисляется через `max(id) + 1`, запись использует простой
`file_put_contents(..., LOCK_EX)`. Эти решения намеренно проще основного контракта
и сохраняются как материал для последующего анализа недостатков.

Автотесты прошли сразу после реализации, но ручной ошибочный HTTP-запрос без
`Accept: application/json` опроверг ожидаемое поведение: Laravel вернул HTML и
`302`, тогда как тестовый JSON-клиент получал `422`. В `bootstrap/app.php` добавлено
правило JSON-рендеринга для всех путей `api/*`; повторный запрос без `Accept` уже
вернул JSON и `422`. Это показало, что зелёного feature-теста было недостаточно.

Рабочий `storage/app/tasks.json` не использовался при проверке. Сервер запущен с
`TASKS_FILE` в отдельном временном каталоге. На отсутствующем файле получен `200`
и `[]`, на пустом — `200` и `[]`, на повреждённом — `500` с безопасным сообщением;
контрольная сумма и содержимое `{broken` после запроса сохранились.

| `rg`, `sed`, Git | Осмотр состояния, спецификации, журнала и рабочей копии | Соблюсти порядок начала сессии и не затронуть чужие изменения |
| shell (`php -v`, `composer --version`) | Проверка обязательного окружения; `php` не найден, Composer также отсутствует в `PATH` | Не подменять непроверенные команды из `AGENTS.md` |

| `apply_patch` | Добавление CRUD, JSON-хранилища, тестов и документации | Выполнить точечные, обозримые изменения |

| Artisan serve, `curl` | Запуск на `127.0.0.1:8000`, успешные и ошибочные запросы | Проверить фактический HTTP-контракт вне тестового клиента |
| Git | Проверка статуса/diff и отдельный коммит | Изолировать наивный прогон от основной реализации |
