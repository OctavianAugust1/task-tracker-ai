## Размышления

Первый этап оставил пять явных `501`-заглушек. В этой сессии бизнес-логика не
пишется: сначала тестами фиксируется внешний контракт `SPEC.md`, после чего должен
быть показан ожидаемый красный прогон.

Спецификация задаёт точное тело для ошибок валидации и код повреждённого хранилища,
но не фиксирует дословные сообщения для каждого `400`, `404` и `500`. Поэтому тесты
не придумывают эти строки: они проверяют единый формат, непустые `code`/`message`
и массив `details`, а точные значения — только там, где они утверждены в `SPEC.md`.

Первый вариант теста пустого `PATCH` ожидал поле ошибки `body`. Это была лишняя
догадка: спецификация требует ошибку, но не задаёт имя поля. До коммита тест
исправлен — теперь он требует непустой список ошибок с текстами, не навязывая
несогласованный контракт. Также отдельным сценарием добавлены неверные типы всех
входных полей и превышение длины `title`.

Красный прогон получен по правильной причине: каждый из 12 новых тестов дошёл до
task-маршрута и получил текущий `501` вместо ожидаемого контрактного статуса. Два
базовых теста каркаса остались зелёными, значит новая тестовая спецификация не
сломала загрузку приложения.

## Использованные инструменты

| Инструмент | Действие | Зачем |
|---|---|---|
| `apply_patch` | Создан журнал до первой правки тестов | Соблюсти порядок начала сессии |
| `apply_patch` | Добавлена контрактная feature-матрица | Зафиксировать `SPEC.md` исполняемыми ожиданиями |
| PHPUnit | Выполнен целевой и полный красный прогон | Доказать, что тесты падают на `501`, а не из-за своей инфраструктуры |
| Laravel Pint | Проверен стиль нового тестового файла | Не коммитить форматные ошибки |
| Git | Проверены diff и состав изменений | Изолировать тестовую спецификацию отдельным коммитом |
