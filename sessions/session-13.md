## Промпты

2. > Подтверждаю

## Размышления

Текущий список принимает один строковый `status`. Запрос требует изменить
публичный контракт, но не задаёт формат списка статусов и семантику даты. Для
статусов возможны повторяемые array-параметры (`status[]=todo&status[]=done`) или
CSV (`status=todo,done`). Для даты возможны точное совпадение, граница «до/после»
или диапазон. Эти варианты несовместимы на уровне клиентов, поэтому по правилам
проекта нельзя выбрать молча.

Рекомендуемый минимальный контракт: `statuses[]=todo&statuses[]=done` плюс
`due_date=YYYY-MM-DD`, где внутри каждой группы действует OR, а между статусами и
датой — AND. Задачи с `due_date: null` при заданной дате не попадают в результат.
Пустые/повторяющиеся/невалидные значения возвращают 422; без фильтров поведение
остаётся прежним. Название `statuses` подчёркивает множественность и не оставляет
двойного типа у старого `status`, но это означает намеренную замену прежнего
query-параметра.

Пользователь подтвердил рекомендуемый контракт без изменений. Спецификация
обновляется до production-кода; затем тесты должны сначала зафиксировать красное
состояние старой реализации.

Красный targeted-прогон дал два ожидаемых падения: `statuses[]` возвращал 422
вместо 200, а старый `status=todo` продолжал возвращать 200 вместо 422. Это
подтвердило, что новые тесты действительно отличают старый контракт от нового.

Для typed boundary добавлен readonly `TaskFilters`. `ListTasksRequest` принимает
только list из 1–3 уникальных разрешённых статусов и точную дату; отдельно
проверяются scalar и associative формы, чтобы они не дошли до defensive runtime
exception как 500. Контроллер передаёт объект сервису, сервис реализует OR статусов
и AND даты. Repository не менялся: фильтрация — бизнес-правило, а не файловый I/O.

Независимый аудит нашёл противоречие старого ограничения SPEC с точной датой,
слишком мягкий count assertion для due-only и недостаточно раздельных unit-веток.
Формулировка ограничения уточнена до диапазонов/«до-после», Feature assertion
заменён exact JSON, добавлены четыре unit-сценария. Повторная проверка подтвердила
все исправления без остаточных Critical/Important.

Реальный HTTP: три создания вернули 201; комбинация `todo|done` + дата вернула
ровно две ожидаемые задачи с 200; дубликаты статуса вернули 422 и две detail-
ошибки. Временный каталог удалён, рабочий JSON не создан.
