## Размышления

Финальная приёмка должна доказывать фактическое HTTP-поведение, а не повторять
результаты feature-тестов. Поэтому Artisan-сервер запускается отдельным процессом,
а запросы выполняются `curl` с фиксацией тел и кодов. Рабочий data-файл проекта не
используется: `TASKS_FILE` указывает в системный временный каталог.

Первый ручной прогон подтвердил отсутствующий, пустой и повреждённый файл; хеш
повреждённого файла до и после запроса совпал. В одной составной shell-команде я
оставил незакрытую кавычку уже после выполненного `curl`: сам HTTP-запрос прошёл,
но вывод тела пришлось показать повторно отдельной командой. Это ошибка команды
проверки, а не приложения.

Независимый ревьюер нашёл три Important-проблемы, которых не заметил зелёный набор
тестов: Laravel 404/405 при debug раскрывали trace и нарушали error envelope,
`"tasks": {}` ошибочно считался пустым массивом, а пустой PATCH возвращал
`field: null` вместо пустого `details`. Причина второй ошибки — декодирование JSON
сразу в associative array, после которого пустые object и array неразличимы.

Все три расхождения исправлены. Заодно добавлена проверка short write. Рассматривал
абстракцию файловой системы ради прямого теста частичной записи, но отверг её как
несоразмерное усложнение учебного локального store: проверка байтов есть в коде,
а отсутствие её отдельного regression-теста честно остаётся Minor-риском.
Повторный аудит не нашёл Critical или Important. Помимо short-write test gap он
оставил Minor: часть общих test helpers допускает лишние поля, а catch-all для
неоговорённых API exceptions отвечает 500, даже если исходный framework status
мог быть другим. Утверждённый контракт от этого не расходится.

После исправлений сервер снова поднят с `APP_DEBUG=true`. Нечисловой ID вернул
контрактный 404 без trace, создание — 201, пустой PATCH — 422 с `details: []`.
Временный каталог удалён, рабочий `storage/app/tasks.json` не создан.
