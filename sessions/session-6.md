## Размышления

Контрактные тесты зависят и от HTTP-слоя, и от ещё не реализованного хранилища,
поэтому сделать весь набор зелёным на третьем этапе невозможно без нарушения
порядка плана. В этой сессии должны пройти только сценарии, завершающиеся до
обращения к хранилищу: query/body-валидация, malformed JSON и JSON-ответ без
заголовка `Accept`. Успешный CRUD и `404` честно сохраняют `501` до этапа 4.

Первый прогон перевёл validation-сценарии в зелёный, но показал warnings из-за
бесполезного `use JsonException` в глобальном bootstrap-файле и неверный `422` для
malformed JSON. Form Request уже видел повреждённый JSON как пустое тело. Проверку
перенесли в ранний API middleware, который использует `JSON_THROW_ON_ERROR` до
валидации. После исправления warnings исчезли, malformed JSON возвращает `400`.

Для списка validation data явно ограничена query-параметрами. Это не позволяет
случайно принять `status` из тела GET-запроса.

## Использованные инструменты

| Инструмент | Действие | Зачем |
|---|---|---|
| `apply_patch` | Создан журнал до правок HTTP-кода | Соблюсти порядок начала сессии |
| Laravel Form Request | Добавлены нормализация, правила и строгие allowlist | Вернуть все ошибки до обращения к хранилищу |
| API middleware | Добавлена ранняя проверка синтаксиса JSON | Отличать malformed JSON (`400`) от validation (`422`) |
| PHPUnit | Выполнены промежуточный и финальный прогоны | Отделить зелёный HTTP-слой от ещё красного CRUD |
| Laravel Pint | Проверен стиль изменённых PHP-файлов | Исключить форматные ошибки |
