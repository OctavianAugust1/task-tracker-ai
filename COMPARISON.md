# Сравнение наивного и управляемого прогонов

Оба варианта решают одну тему — API списка задач на Laravel 12 с JSON-файлом, —
но создавались разными способами. Наивный вариант находится в `naive-run/`,
основной — в корне проекта.

## Что наивный вариант решил за пользователя

| Решение | Наивный прогон | Решение в спецификации |
|---|---|---|
| Поля задачи | `id`, `title`, `completed` | `title`, `description`, `status`, `due_date`, timestamps |
| Статусы | Один boolean `completed` | `todo`, `in_progress`, `done`; любые переходы |
| Ответ списка | JSON-массив без оболочки | Единая оболочка `{"data": [...]}` |
| Формат файла | Массив задач | Объект с монотонным `next_id` и `tasks` |
| Новый ID | `max(id) + 1` | `next_id`; удалённые номера не используются повторно |
| Неизвестные поля | Не определено контрактом | Строго запрещены, все ошибки возвращаются вместе |
| Повторный PATCH | Не описан заранее | Идемпотентный `200`, timestamp и файл не меняются |
| Повреждённый файл | Безопасный `500`, но структура проверяется слабее | Строгая проверка корня, служебных полей и каждой задачи |
| Параллельная запись | `LOCK_EX` только на финальной записи | Lock на всём read-modify-write и atomic rename |
| API-ошибки | Исправлены до JSON после ручного обнаружения `302` | Единая оболочка, включая framework 404/405 и internal 500 |

## Что изменилось после спецификации

Спецификация заставила принять неоднозначные решения до кода: разрешённые статусы,
поведение пустой выборки, неизвестных полей, несуществующего ID, повторного PATCH,
прошедшей даты и трёх состояний файла. В наивном прогоне эти решения сделал агент,
причём часть возможностей (`description`, `status`, `due_date`) просто отсутствует.

Основная реализация начала с 12 падающих контрактных тестов. После HTTP-слоя шесть
из них стали зелёными, а шесть продолжили получать честный `501` до появления
store. Это показало границу этапов лучше, чем итоговый зелёный прогон.

Независимый аудит основной версии нашёл три Important-расхождения, несмотря на
полностью зелёные тесты: stack trace в framework 404, принятие `tasks:{}` как
пустого массива и неверные details пустого PATCH. Все исправлены, тесты усилены.
В наивном варианте такой контрактной сверки не было.

## Где наивный прогон оказался лучше

Наивный вариант был заметно короче и быстрее доведён до работающего CRUD. Для
одноразового локального прототипа его полей и пяти feature-тестов могло бы хватить.
Он также помог поймать практический Laravel-дефект: без `Accept: application/json`
ошибочный реальный запрос сначала вернул HTML и `302`, хотя тестовый JSON-клиент
был зелёным.

Цена этой скорости — неявный контракт и хрупкая запись. Увеличивать такой сервис
опаснее: смена `completed` на статусы, исправление повторных ID и добавление
атомарности потребовали бы менять уже существующие данные и ответы клиентов.

## Проверяемый итог

- наивный прогон: 5 feature-тестов, 23 assertions;
- основная реализация до исправлений аудита: 23 теста, 289 assertions;
- основная реализация после исправлений аудита: 24 теста, 279 assertions
  (снижение числа assertions связано с заменой широких проверок на exact JSON);
- обе версии запускались реальным HTTP-сервером с отдельным временным файлом;
- основной вариант дополнительно проверяет конкурентные процессы, файловые сбои,
  строгую структуру данных и framework-ошибки.

Вывод: наивный прогон быстрее дал демонстрацию CRUD, но спецификация перенесла
решения от агента к пользователю и сделала поведение измеримым. Основная ценность
управляемого прогона — не объём кода, а возможность обнаружить расхождение до того,
как оно станет форматом данных или публичным API.
